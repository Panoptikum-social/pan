Don't lead with a plausible-sounding narrative built only from reading code/git history when a live system (DB, logs, a connected tool like tidewave) is available to check the actual shape of the problem first.

**Why:** during project_import_stale_stall_sept2026, asked to explain a 20k-podcast stale backlog, I proposed two successive theories from code/memory alone — "capacity outgrew a single-threaded worker" and "crash-storm cost accumulated via the 60s/10s backoff" — both implicitly predicting *gradual* decline. The user rejected both sharply ("pure bullshit", "plain wrong") and pointed out podcast count had actually *decreased* recently. Only querying the DB directly (`podcasts.next_update`/`updated_at`, `episodes.inserted_at` hourly counts) revealed the real shape: a sudden step-function cliff at one timestamp, which immediately falsified both gradual theories and pointed at a transient runtime wedge instead.

**How to apply:** when investigating "X suddenly got worse" / "this broke" reports on a project with DB or log access available (tidewave here), query for the actual timeline/shape of the anomaly (cliff vs. drift, one-time vs. recurring, correlated with a specific timestamp/deploy/host) *before* proposing a root-cause narrative — even a well-reasoned one grounded in real code and past commits. Code-only analysis is fine as a source of *candidate mechanisms* to check against the data, not as the basis for the initial diagnosis itself.
