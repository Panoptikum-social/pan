In this codebase, DB-level FKs are almost always declared `references(..., on_delete: :nothing)` in migrations, so cascading on delete only happens if the Ecto schema association explicitly sets `on_delete: :delete_all` (Ecto performs the cascade itself via extra queries, not the DB). Any `belongs_to` relation pointing at a model that ISN'T declared as a `has_many .../on_delete: :delete_all` (or `many_to_many .../on_delete: :delete_all`) on the parent schema will raise a FK constraint error on `Repo.delete!`, or — if there's no FK constraint at all (e.g. a plain indexed integer column like `personas.redirect_id`) — silently leave a dangling reference.

**Why:** found while building a proper `PersonaController.delete/2`. `PanWeb.Persona`'s schema declares `on_delete: :delete_all` for `:engagements`, `:thumbnails` (Image), `:manifestations`, and the `:episodes` many_to_many (which cleans up the `gigs` join rows) — but NOT for `Like`, `Follow`, or the `:delegates` many_to_many (`delegations` table, both `persona_id` and `delegate_id` sides). Those needed manual `Repo.delete_all` before `Repo.delete!(persona)`. `redirect_id` on other personas pointing at the one being deleted has no FK at all, so it needed an explicit nullify pass to avoid dangling refs.

**How to apply:** before writing any "delete X properly" action, read the target schema's associations for `on_delete: :delete_all`, then check migrations for any `references(:table_name)` pointing at it that ISN'T covered by one of those associations — those need explicit `Repo.delete_all`/nullify calls in the delete action, wrapped in `Repo.transaction`. Applies to any model with several inbound associations (Podcast, Persona, Category, etc.), not just Persona.

See also [manticore-delete-sync](manticore-delete-sync.md).
