Found 2026-09-01 while cleaning up stale deps (project_dep_cleanup_sept2026). `httpoison` is stuck on 2.3.0 because 3.0.0 requires `hackney ~> 4.0`, while `tzdata` (pulled in transitively by `timex`, the only thing requiring it) hard-pins `hackney ~> 1.17`. Confirmed by actually bumping `httpoison` to `~> 3.0` locally and running `mix deps.get` — resolver fails exactly as expected, then reverted.

**Considered dropping `timex` instead** (would free `tzdata`/`hackney` with no client-swap needed) but user and I agreed against it: only 2 files use `Timex` — `activity_pub/view.ex`'s `from_now/1` (trivial to replace) vs. `parser/helpers.ex`'s `Timex.parse/2`, the engine behind the ~70 `@date_formats` custom patterns (see [feed-compliance-checker](feed-compliance-checker.md)). Reimplementing that by hand risks silently re-deriving years of accumulated real-world-feed date-parsing bugs. Decision: keep `timex`.

So the only way to unstick `hackney` is moving off `httpoison` — 10 call sites (`updater/feed.ex`, `parser/category.ex`, `parser/download.ex`, `activity_pub/net.ex`, `search.ex`, `search/manticore.ex`, `bot.ex`, `updater/podcast.ex`, `pan_web/models/podcast.ex`, `page_frontend_view.ex`), all plain `HTTPoison.get/head/post(url, headers, options)` with no query-builder/proxy/cookie usage — mechanically swappable to [Req](https://hexdocs.pm/req).

**Checked actual exploitability before treating this as urgent** — pulled all 4 open hackney CVE advisories (osv.dev EEF-CVE-2026-47075/47076/47071/47069) and checked each against real usage, not just the label:
- CVE-2026-47071 (SOCKS5 TLS-upgrade DoS, rated HIGH) — not applicable, no proxy config anywhere in the app.
- CVE-2026-47069 (CRLF in cookie domain/path, LOW) — not applicable, no cookie-setting via hackney anywhere.
- CVE-2026-47076 (SSRF allowlist bypass via percent-encoding, MEDIUM) — not applicable, but for a worse reason: see project_ssrf_guard_feed_fetches.
- **CVE-2026-47075** (CRLF/header injection via URL, MEDIUM, fixed in hackney 4.0.1) — **the only one that's real here**. Feed `self_link_url`/enclosure URLs are attacker/podcaster-controlled and flow unvalidated straight into `HTTPoison.get/head`. Bounded impact though: header injection against the remote feed server, not against Panoptikum itself.

**Verdict:** worth doing, not urgent. One bounded MEDIUM finding, fixable by a client swap whenever convenient — schedule as normal hardening, not a hotfix. Lesson worth remembering: a CVE's own severity rating is for the library used in the abstract, across every possible call pattern — always check it against the actual call sites before deciding urgency (3 of 4 turned out inapplicable here).

User asked (at the time) that this be tracked in Claude's notes only, not in backlog.md.
